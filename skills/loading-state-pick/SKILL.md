# loading-state-pick — 等待的形态是一门取舍

## R — 原文（Reading）

> ▪加载等待优先用骨架屏而不是转圈：骨架屏让用户感觉更快，转圈适合1 秒内能完成的操作。
>
> — 《Vibe Coding 前端交互效果术语手册》附录C 第5条

> 数据返回前显示与真实布局一致的灰色骨架占位块，带缓慢的明暗呼吸动画，数据到达后替换为真实内容。
>
> — 同上，第二章 Skeleton Screen

> 统计数字滚动到可见区域后，从0 递增到目标值，持续2 秒，末尾减速，带千分位逗号。
>
> — 同上，第二章 Count Up（计数类，是"超过 1 秒"的例外之一）

---

## I — 方法论骨架（Interpretation）

大多数人做加载态是反射性的：要等，就放个转圈。这本书把这件事变成一道**三变量的分派题**。

**变量一：等待有多长。** 分界在 1 秒。1 秒内的等待来不及生成"不确定感"，转圈的成本可以忽略；超过 1 秒，转圈就开始收费——它只传达"还没好"，零结构、零进度，注意力无处安放，不确定感随时间超线性增长。

**变量二：结构可不可预期。** 如果你已经知道出来会是什么形状（列表、卡片流、个人中心），就用这个形状的灰色轮廓占位——**骨架屏传达的是"结构已就位，只差内容"**，用户能预判完成形态，注意力有落点，主观时间被压缩。这是本书最反直觉的一条：它优化的是**感知速度**，不是真实速度。转圈在这件事上什么都不做。

**变量三：有没有真实进度。** 上传、导出、长任务——进度是已知的，就该显式显示（进度条 / 环形进度）。让用户看一个不知何时结束的转圈，是对已知信息的浪费。

再加两个特例：
- **多步流程**（下单、注册）→ 步骤条，回答的不是"还要多久"而是"走到第几步了"。
- **结构不可预期的文本生成**（AI 回答）→ 打字机 / 流式，让内容边生成边出现——这其实是"把等待切碎"，比任何占位都有效。

一句话概括这个方法的判断依据：**选形态的标准不是哪个组件更好实现，而是用户在这段时间里能看到什么有意义的信息。**

## A1 — 书中的应用（Past Application）

### 案例 1：骨架屏 vs 转圈的分界（附录C 第5条）
- **问题**：列表要等三秒，页面中央一个转圈转三秒。
- **方法论的使用**：估等待时长（3s，超过 1s 分界）+ 判结构可预期性（列表结构固定，可预期）→ 骨架屏。
- **结论**：三秒被体验成八秒，不是因为它真的慢，是因为用户不知道在等什么、等出来长什么样。
- **结果**：换成与真实布局一致的灰色骨架块 + 缓慢明暗呼吸，数据到达后替换。作者同时给了反向边界：骨架一闪而过会制造闪屏，短操作别用。

### 案例 2：数字滚动的 2 秒（第二章 Count Up）
- **问题**：统计数字从 0 递增到目标值，需要多长？
- **方法论的使用**：这不是"移动"，是"呈现"——用户需要时间读数字变化，不能套用入场动画 0.4–0.8 秒的区间。
- **结论**：给 2 秒，末尾减速，带千分位逗号。
- **结果**：这条恰好是全书"超过 1 秒会显得拖沓"这条硬边界的**例外**，但作者没把这个区分写出来——见 B 段。

### 案例 3：AI 对话界面的打字机（第二章 Typewriter）
- **问题**：回答要等好几秒，而且你不知道会出来多长。
- **方法论的使用**：结构不可预期 → 骨架屏不成立（你没法定轮廓）→ 用逐字呈现把等待切碎。
- **结论**：字间隔 80 毫秒，末尾光标闪烁，打完保持闪烁。
- **结果**：这是全书唯一一处覆盖"不可预期内容"的等待形态，虽然作者没把它归为等待态设计。

### 案例 4：无限滚动的两层状态（第三章 Infinite Scroll）
- **问题**：滚到底自动加载，加载中和加载完分别显示什么？
- **方法论的使用**：加载中 → 转圈（局部、短、结构可预期）；没有更多 → 终止态"到底啦"。
- **结论**：等待形态要覆盖"结束"，否则用户会一直往下滚。
- **结果**：这条只有单点依据（见 `rejected/r10`），本 skill 作为检查项保留。

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个 skill？

1. 新做一个列表 / 详情页 / 个人中心，要定加载态。
2. 现有页面只有一个转圈，用户觉得慢、跳出率高。
3. AI 功能（对话、生成、分析）要等 5–30 秒，不知道界面该显示什么。
4. 上传 / 导出 / 批量处理，有进度但没显示。
5. 多步表单或下单流程，需要告诉用户走到哪了。
6. 无限滚动列表，不知道"到底了"该怎么呈现。

### 语言信号（出现这些都会命中）

- "加载中显示什么" / "要不要加个骨架屏"
- "用户要等好几秒" / "等太久用户会跑"
- "现在是个转圈，感觉不太行"
- "AI 回答要等很久，中间显示什么"
- "上传进度怎么显示"
- "滚到底了怎么提示"

### 与相邻 skill 的区分

- **vs `interaction-brief`**：本 skill 只做**选型**（选哪种形态），选完由 brief 写成规格。**判断线：用户是在纠结"用什么"，还是已经定了"要怎么写"。**
- **vs `motion-audit`**：audit 会说"长等待用转圈是错的"，但不说该换成什么。本 skill 给处方。
- **vs `motion-param-calibrate`**：骨架屏的呼吸周期、进度条的增长曲线由 calibrate 取值——**尤其注意：呼吸是循环类，必须加"缓慢"。**

## E — 可执行步骤（Execution）

### 零、如果对方是新手，先读这一条

新手在这个话题上的问题几乎只有一句：**「要等，我放个转圈行不行？」**

**默认答案分三种，直接给结论，不要先问变量**：

| 他的情况 | 直接告诉他 |
|---|---|
| 等不到 1 秒（本地点一下、切个 Tab） | **别放任何东西。** 放了反而显得慢——本来没感觉，一加转圈，人就开始计时 |
| 等 1–3 秒，出来的是列表、卡片、表格 | **骨架屏**。这是他这个场景的默认答案 |
| 等超过 3 秒，不知道要等多久 | **骨架屏 + 一句「正在加载，大约还要几秒」**。只有骨架屏没有文案，用户会以为页面坏了 |
| 上传文件、导出、安装 | **进度条**，而且只用真进度。假进度走到 90% 卡住，比没进度更让人想关掉 |

**两件事必须替他说清**：

1. **别做全屏加载页。** 新手很喜欢把 loading 做成品牌动画，觉得「显得用心」。实际效果是：本来 2 秒的等待，被 3 秒的动画拖成 5 秒，而且每进一次都要看一遍。**加载页是最容易被做成反效果的地方。**
2. **等待本身可能是能修的。** 接口 8 秒，正确做法是把接口修到 1 秒，不是研究这 8 秒放什么好看。这一条要在最前面说，不要等讲完形态才顺口提一句。

**新手最需要的一句话**：

> 加载态的作用是**让等待不那么难熬**，不是**让慢变得合理**。

---

1. **估等待时长。**
   - 三档：< 1s / 1–3s / > 3s 或不确定。
   - 完成标准：有一个档位。估不出来就问"这个请求通常多久回来"，或用"不确定"档。
   - 判停条件：若等待来自可优化的后端/查询，**先说"这个等待本身可能不该存在"**——形态优化救不了 10 秒的接口。这是本 skill 的第一道边界。

2. **判结构可预期性。**
   - 出来的是固定形状（列表 / 卡片 / 表头+行 / 图文块）→ 可预期。
   - 出来的是长度与形状都不定的内容（AI 生成的回答、未知格式的报表）→ 不可预期。
   - 完成标准：二分。

3. **查有无真实进度。**
   - 有百分比 / 已传字节 / 已完成步数 → 有。
   - 完成标准：三分变量齐了（时长 / 结构 / 进度）。

4. **按分派表选形态。**

   | 时长 | 结构 | 进度 | 形态 |
   |---|---|---|---|
   | < 1s | — | — | **不放加载态**，或按钮内小转圈（见第 5 步） |
   | 1–3s | 可预期 | 无 | **骨架屏**（与真实布局一致） |
   | > 3s | 可预期 | 无 | **骨架屏** + 文案说明在做什么 |
   | 任意 | 可预期 | 有 | **进度条 / 环形进度** |
   | 多步流程 | 可预期 | 有（步） | **步骤条** |
   | 任意 | 不可预期 | 无 | **打字机 / 流式呈现**（把等待切碎）；若必须占位，用骨架 + 文案兜底 |
   | 局部追加（列表下一页） | 可预期 | 无 | **列表底部小转圈** + 终止态 |

   - 完成标准：选定一种，并能说出为什么不是另外几种。

5. **补边界与终止态。**
   - 提交类按钮：加载态必须**禁用重复点击**，且给三态（正常 / 提交中 / 结果）。
   - 骨架屏：必须与真实布局**尺寸一致**，否则内容替换时页面跳动，比不放更糟。
   - 骨架屏：1 秒内返回的请求不要用（会闪）。
   - 列表：必须有终止态（"到底啦"）。
   - 完成标准：这四条都过了一遍。

6. **交给下游写成规格。**
   - 骨架屏的呼吸动画、进度条的增长动画 → `motion-param-calibrate`（循环类必须"缓慢"；增长类用 ease-out）。
   - 完整描述（尺寸、时长、替换方式、兜底文案）→ `interaction-brief`。
   - 完成标准：用户拿到的是可执行的下一步，不是"用骨架屏吧"。

## B — 边界（Boundary）★

边界分两类，混淆这两类会导致该拦的事没拦。

### 第一类：直接转出，不要介入

- **形态已经定了，要成稿。** → `interaction-brief`。
- **形态定了，要调呼吸周期 / 增长曲线。** → `motion-param-calibrate`。
- **要审整页动效是否过多。** → `motion-audit`。

### 第二类：必须介入，但第一句是拒绝

这一类是本 skill 最重要的用法：**用户来问"选什么"，往往真正需要的是"这个等待不该存在"。**

- **等待本身不该存在。** 接口要 8 秒、用户想做个"特别好看的全屏加载页"——必须介入，第一句是"这 8 秒大概率不该存在"，并给优化方向（分页 / 缓存 / 流式 / 预取 / 骨架+增量渲染），**再**谈形态。直接开始设计加载页，等于帮用户把慢合理化。
- **加载态会干扰主任务。** 后台静默刷新、乐观更新、< 300ms 的请求——介入，结论是**不显示任何加载态**。书中默认所有等待都该有可见反馈，这是它作为 2025 年展示页手册的时代局限，不是规律。
- **不可预期、又必须等、且没有流式能力。** 介入，给退路："骨架 + 文案 + 超时兜底 + 可取消"，**不要硬套打字机**（没有流式做不出逐字出现）。
- **需要完整状态机。** 并发请求、重试、部分失败、取消、超时——介入，说明这超出本书范围，建议按四态（loading / success / error / empty）单独设计，而不是只做 loading 这一态。

### 作者在书中警告的失败模式

- **长等待用转圈** → 零结构零进度，三秒被体验成八秒，用户退出或反复刷新造成雪崩（x06）。
- **短操作用骨架屏** → 骨架一闪而过，制造闪屏（p15 的 violation 描述）。
- **加载态无限叠加** → 同一页同时存在骨架屏 + 转圈 + 进度条，属于注意力预算超支（`motion-audit` 组一）。

### 作者的盲点 / 时代局限（蒸馏者补充，非书中观点）

- **1 秒阈值是经验值，不是定律。** 它来自人对因果延迟的感知窗口（约 100ms / 1s 两个坎），不是物理常量。网络慢的设备上，300ms 的等待也该给反馈；极快的接口上，1.5 秒用骨架屏反而制造闪屏。判断应以"用户是否已经感觉到停顿"为准。
- **骨架屏有一个书中没提的硬要求：必须与真实布局尺寸一致。** 尺寸不一致会导致内容替换时页面跳动（CLS），这个副作用比"没有骨架屏"更糟。作者只说了"与真实布局一致"，没解释为什么这是硬要求。
- **没有讨论"不显示加载态"这个选项。** 对乐观更新、缓存命中、< 300ms 的请求，最佳加载态是"没有加载态"。本书默认所有等待都需要可见反馈，这是它作为 2025 年展示页手册的时代局限。
- **没有讨论失败态。** 骨架屏加载失败怎么办、进度条卡在 90% 怎么办——全书零提及。任何加载态都必须配一个失败态与超时兜底。

### 容易混淆的邻近方法论

- 感知性能优化（Perceived Performance）——同一族，但范围更大（含预加载、优先渲染首屏等），本 skill 只覆盖"等待期间的可见反馈"。
- 状态机设计（loading / success / error / empty）——四态齐全才是完整方案，本 skill 只管 loading 这一态。
